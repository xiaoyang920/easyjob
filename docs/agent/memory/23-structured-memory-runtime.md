# 博客助手：画像、约束与历史决策

当前实现采用用户/会话两个范围，不引入项目实体，也不增加顶层 action 或独立分类 LLM。

## 数据与运行状态

| 内容 | MySQL | 本次运行 State | 加载方式 |
|---|---|---|---|
| 技术背景、长期表达偏好 | `user_profile` 的结构化字段 | `user_profile` | 每次请求开始读取 |
| 当前仍有效的要求 | `user_memory`，`memory_type=constraint` | `active_constraints` | 加载用户级及当前会话级有效记录 |
| 用户明确确认的历史结论 | `user_memory`，`memory_type=decision` | 检索后进入 `task_results` | Main 选择 `retrieve(target=memory)` |
| 旧历史事件（归档） | 保留既有 `user_memory`，`memory_type=event` | 不加载、不召回 | 管理页独立分页查看或删除 |
| 本次临时忽略的要求 | 不持久化 | `constraint_overrides` | Main 指定已知约束 id |

`source_conversation_id` 记录来源，`scope_conversation_id` 决定会话级记录适用范围，两者不能混用。`scope=user` 可跨会话使用；`scope=conversation` 只对相应会话生效。当前显式检索只返回用户级和当前会话级有效决策，不把另一篇文章的会话约定直接带入当前任务。旧 event 记录即使数据库状态仍是 active，也不会进入启动上下文或检索结果。

画像读取真实结构字段，不依赖可能过期的 `summary`。后台事件提取已关闭：不再创建提取任务，每六轮与关键词触发均失效；已有待处理任务直接结束，不读取历史或调用模型。普通对话保留在消息和会话摘要中，不成为长期记忆。保留旧归档数据，不自动删除或衰减用户的历史记录。

一般写作/表达约束由 Main 和执行模型结合当前任务遵守。联网限制采用受控键 `web_search=deny`，执行权限层会剔除 web_search，即使 checkpoint 的能力列表被扩大也不能调用。`allow` 或临时覆盖仅解除用户自己的限制，不能突破服务端禁用政策；其他自由文本约束不被宣传为后端可机械校验的强制规则。

## 一轮 Main 的职责

消息顺序为：`SystemMessage(固定规则)` → `HumanMessage(带标签的上下文数据)` → `HumanMessage(当前问题)`。画像、约束、检索原文不拼进系统提示词。它们是当前用户的数据，不授予工具能力或取消后端身份隔离。

Main 在现有结构化响应中附带 `memory_changes`，最多 8 条，每次运行最多提交一个批次。没有额外的意图分类模型，也没有第五种动作。示例：

```json
{
  "action": "answer",
  "reply": "好的，以后默认简短回答。",
  "memory_changes": [{
    "kind": "profile",
    "operation": "set",
    "scope": "user",
    "key": "preferences.detail",
    "value": "brief",
    "source_quote": "以后默认简短回答"
  }]
}
```

Main 根据当前用户明确表达判断是否持久化。`source_quote` 必须出现在原始当前请求，后端不接受历史消息、图像识别扩展文本或工具结果作为写入依据；模型不能指定 user_id、conversation_id、执行 token 或授权能力。这个校验约束来源和结构，语义上“是否明确、是否确认”的判断仍由 Main 完成，需要真实模型验收。

- “这次简单说”：不修改长期画像，在本轮回答和任务指令中覆盖表达方式。
- “这次不用这个要求”：输出 `constraint_overrides=[已有id]`；本轮 Main 及执行上下文忽略该要求，下次请求恢复。
- “以后默认简短”：更新画像偏好。
- “取消这个要求”：以已知 record_id/key/scope 提交 remove，旧记录设为 inactive。
- “改成面向有经验的人”：停用已知旧记录，再新增新内容，保留历史。
- “我们决定采用教程形式”：保存 decision，不在下次启动时当作有效约束注入。

修改或取消约束/决策必须引用当前有效约束或本轮成功召回的记忆 id。找不到旧决策 id 时可以先检索，再在下一轮提交变更。新键不能悄悄覆盖已有 active 记录；同批次不能重复修改同一字段。profile 的列表字段采用明确的完整值替换，偏好按单个 key 更新或删除。

State 是本次运行的快照；下一请求按可信 user_id/conversation_id 重新读取数据库。原始聊天消息保留，当前状态独立管理，不从旧摘要复活已失效规则。Main 的 `action_history` 是执行日志，不属于业务决策记忆。Analysis 仅得到有效约束和声明依赖；Main 的草稿生成得到画像、有效约束和声明依赖，临时覆盖也传入写作子图。

## 持久化与向量一致性

后端校验完整动作、引用与变更来源后，再提交变更。事务锁定当前有效 agent_run 及用户画像行：取消/过期/错误 token 的执行者不能写入；同一用户的不同会话串行修改，画像按当前加载值检测并发冲突。MySQL 写入与 `user_memory_change` 幂等回执一起提交；相同 run 重放不重复新增，内容不同的重放拒绝。保存失败不会交付“已记住”的正常回答。

约束不进向量索引，直接按范围和状态查询。decision 进入现有 `user_memories` 索引；MySQL 始终校验 owner、scope、status、type。`memory_sources` 与公开文章 citations 分开，旧引用编号不能成为公开事实证据。

变更回执同时保存待同步向量操作。提交后尝试同步，单次最长 15 秒；失败保持待同步状态。后续显式召回先按用户重试待同步操作，每次最多 8 批，有剩余积压或失败时报 tool_error，不伪装成成功未命中。重试前再次检查 MySQL active 状态，旧 upsert 不会恢复失效决策。ES 删除延迟不影响旧记录在 MySQL 被过滤。启动画像/约束读取不触发 embedding 或索引同步。

启动上下文最多 32 条有效约束，画像结构最多 4000 字符；超出预算明确失败，不默默丢弃要求。Main 的总预算和原有只读恢复次数仍适用。流式活动仅显示“更新记忆”等状态，不广播画像、约束正文或变更引用。
