# 任务结果按需读取改造计划

状态：已实施并验收。制定日期：2026-10-25。具体结果与性能取舍见 [结果读取验证](37-result-access-validation.md)。以下保留实施方案；“真实对照”是同一当前实现的策略开关对照，不能当作完整旧版本基准。

## 目标与已确认现状

完整执行结果保存在 AgentState.task_results。Main 的模型请求只包含当前有用的结果或片段；后端按需读取当前执行状态，不为每次回读另查 Redis Checkpoint。

已确认 action_runtime.execute_tool_node 会将 state.task_results 传给 read_task_result。context_tools.read_task_result 已从该映射取正文，并校验公共结果权限和引用来源。Checkpoint 在图运行时按现有机制持久化，在恢复运行时还原状态；本计划不承诺消除 LangGraph 自身的 Checkpoint I/O。

当前不足：Main 有空间时会扩展到全部结果；空间不足时采用固定软预算投影；结果读取只有单份字符范围，查找后半段信息可能需要多次决策；没有明确记录跨回读任务的已载入片段覆盖范围。

## 一、建立统一结果目录与来源定位

修改 context_projection.py，给公开结果生成轻量目录，字段包括 task_id、tool_name、instruction、状态、字符数、Token 估算、引用 ID/标题、内容版本标识和可用读取方式。

目录从已有结果元数据生成，不另调摘要模型。没有正文时明确标记 index_only，不将目录、标题或摘要当作已读证据。原始 result/citation_contents 保持原样。

保留所有旧字段兼容性；新元数据缺失时可以从 task_results 推导，不要求批量迁移已有 Checkpoint。结果版本标识只用于定位/覆盖范围一致性，不能代替已有公共来源权限与版本校验。

## 二、按当前步骤选择正文

修改 main_agent.py 的模型视图组装，使用确定的优先级：

1. 当前用户输入、有效要求、必要私有上下文及既有完整轮次历史。
2. 刚执行完成、供本次 Main 判断下一步的结果；最近主动请求读取的片段。
3. 当前步骤明确需要的依赖、已选证据和其他小结果。
4. 较早的大结果仅保留目录，需要时再读取。

将现有“完整结果集合放得下就全部带入”改成按上述优先级逐份准入。32K 保留为初始结果软预算，在本步明确需要的结果上允许利用额外空间；不因为窗口有空余就重新带入所有旧资料。单份大结果的初始判断阈值设为可配置的 8K Token，最终数值根据真实对照确定。

总窗口 256K、触发点 192K、压缩后整体目标 64K继续约束完整请求。计入图片、Schema、输出预留和字符限制，不截断近期完整问答，也不在刚压缩后立即把窗口重新填大。超大必要输入明确失败或要求缩小范围。

## 三、支持定位和批量回读

先扩展 read_task_result，保留 source_task_id/start_char/max_chars 旧参数；增加互斥的定位模式：字符范围、关键词上下文、引用 ID。关键词定位使用本地文本匹配，不新增模型、向量索引或外部检索；无匹配时如实返回未找到。

再增加 read_task_results 批量入口，共用同一读取实现，一次最多选择 4 份来源。整批共享字符/Token 预算，逐项返回实际读取范围、source_task_id、版本、引用、has_more 和继续读取位置，不把每项上限相加造成超预算。定位后直接返回片段，避免再经过一次只返回位置的模型决策。

相关文件：models/main_tool.py、services/main_tools.py、services/context_tools.py、graph/action_runtime.py、Main 提示与上下文读取计数。新工具注册、能力检查、超时、批量总量与调用次数一起落实。

## 四、维护已读取片段，避免反复复制

回读结果记录原始 source_task_id、内容版本、起止范围及来源引用。合并同一来源重叠范围时使用元数据定位，不能按相似文字误合并不同来源。

Main 视图优先保留本步实际读取的片段，重复读取返回同一来源定位；读取结果不被展示成新的独立资料，回读的回读应解析回原始来源，防止 JSON 包装层层套叠。旧的回读结果缺少元数据时按旧格式处理。

本轮可用证据范围以实际发送给模型的内容为准。“以前读过”但已从上下文省略的正文不等于这次仍然可见；Main 如需再次引用，应重新载入。未载入内容不能被模型生成的分析产物或回答依赖间接绕过。

## 五、权限、持久化和恢复边界

公开结果读取始终限定到后端提供的当前运行可读结果。上一轮结果只有经现有恢复/复用流程授权进入该范围后才允许读取；参数不能指定任意 user_id、run_id 或 Redis key。

继续执行能力校验、联网约束及公共文章来源版本检查；批量每项独立校验，不因另一项合法而放过非法项。私有草稿、编辑器和记忆仍走现有专用权限路径，本阶段不扩大通用读取器权限。

新增读取覆盖元数据随当前状态持久化；恢复运行先还原 AgentState，再从当前 task_results 读取。旧 Checkpoint 缺少新字段时安全默认，保持引用编号稳定。恢复与同一轮的普通回读分开验证。

## 六、验收及上线顺序

按目录/定位读取、Main 选择策略、批量/片段复用、恢复兼容的顺序实施，每步使用相应测试。全部通过后重启部署本地服务，并以实际网站链路验证。

必要验收：

- 小结果和普通新检索结果不因目录策略多绕一次模型读取。
- 已知关键词在长结果尾部时，一次定位回读能取得正确原文；一次批量请求可获取多份目标结果。
- 超过窗口、最近完整对话、压缩后目标、字符限制及私有必要输入得到正确处理。
- 正文哈希与引用保持一致；只见目录或部分片段不能宣称读完全文，不能把未载入来源当作证据。
- 跨用户/运行读取被拒绝，联网限制和来源变更仍生效；旧检查点可恢复。
- 回读器直接访问当前状态；记录其没有额外调用 Checkpointer。恢复测试则验证实际从 Redis 还原后还能正确回读，两者不能混为一种测试。

真实模型对照保留三组：当前自适应内联、新方案、固定 32K 旧策略。使用相同模型与输入，覆盖新结果即时回答、旧结果定位、多结果比较、确实需要全文四类，记录答案正确率、模型调用数、读取次数、供应商输入/输出 Token 和端到端耗时；重复样本并报告波动。新方案不预设所有场景都同时更省 Token 和更快，若常见即时回答明显退化，需要调整准入策略后再启用。

另做完整 HTTP -> Java -> Agent -> 模型验证和真实 Checkpoint 中断恢复验证，创建独立测试身份并清理，不能以纯内存状态序列化代替 Redis 恢复。

保留配置开关回退到当前自适应内联方案，回退不删除 task_results 或修改已产生的业务结果。最终报告明确测试覆盖范围和仍存在的性能取舍。
