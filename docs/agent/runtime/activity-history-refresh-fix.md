# 刷新后活动记录还原

## 问题与原因

成功回答在首次 SSE 展示时有活动、计划、说明和耗时，但历史接口只为失败及特殊成功任务还原这些字段。刷新后只剩回答正文和 runId，前端查询运行状态时创建空活动状态，产生“处理完成 · 0 项活动”“0 秒”“正在准备处理请求…”的组合。

此外，已还原的成功状态在再次读取运行状态时会重设 finishedAt，使历史耗时随刷新变化。

真实接口验证还发现时区混用：运行、SSE 帧和节点事件的创建时间由 MySQL 的 CURRENT_TIMESTAMP 默认生成，使用数据库会话时区；运行结束更新使用 UTC_TIMESTAMP。当前本地数据库时区为 SYSTEM（上海时间），直接把创建时间加 Z 会产生负 8 小时的耗时。

## 修复

- 历史接口在当前分页的用户轮次内，同时查询普通成功和失败任务；仍按用户、会话和轮次过滤，批量获取公开活动事件。
- 根据 runId 或已提交的 assistant messageId 关联回答，恢复 agentEvents、runStartedAt、runFinishedAt、runStatus。保留原回答，避免重复消息，不把别轮记录挂到当前回答。
- SSE 活动过期时，沿用持久化节点事件回退。未保存任何明细的旧回复显示“该回复未保留处理明细。”，不显示准备中或虚构的 0 秒。
- 已完成状态再次确认时保留原始结束时间；任务恰好在首次历史读取后完成时，再读取一次历史以还原提交结果与活动。
- 缺少开始或结束时间的旧记录保持未知，前端隐藏无法确定的总耗时。
- 历史查询通过 CONVERT_TZ 将数据库本地创建时间转换为 UTC，再与已有 UTC 结束时间组合；SSE 帧、节点事件和无输入锚点的旧轮次匹配使用同一转换。不改写现有数据库记录。

无需数据库迁移。此处读取展示记录，不恢复图执行，不重新调用模型。

- 前端：`agentStream.test.mjs`、`agentIncomplete.test.mjs`。
- 浏览器：`agent-run-history.spec.ts`，覆盖成功刷新、完成与读取并发、旧记录缺少明细、失败记录和核验警告；`agent-plan.spec.ts` 覆盖计划全文还原。
