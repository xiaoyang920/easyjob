# 文章分批向量化与线程池配置

MQ 消息仍然按文章投递。4个索引消费者持有各自文章的索引锁，分块后调用 `ArticleEmbeddingService`，把批次提交到整个 Java 实例共享的8线程 `articleEmbeddingExecutor`。每批最多16块，每篇文章最多同时提交4批；一个批次完成后才补充下一个批次。消费者从完成队列收集结果，成功批次数达到总批数才继续。不会一次提交最多32批而挤满队列。

工作线程只生成向量，不写 ES、不更新 Outbox、不确认 MQ。消费者按批次起始位置把结果放回原数组；供应商返回的向量也按 `index` 配对，拒绝重复或越界编号。所有批次成功且向量校验通过后，消费者统一 Bulk 写入 ES、校验文章版本、清理旧块、更新全文索引，最后完成 Outbox 并从监听器返回，由容器确认消息。Bulk本身不是事务，部分写入失败继续通过固定分块ID幂等重试。

任一批次失败、拒绝、超时或消费者中断时，尝试中断其他批次，并移除尚未开始的任务，不进入本次 ES 写入/Outbox成功流程。总超时包含提交、排队和向量化，不包含后续ES请求。HTTP客户端可能不能立即响应中断；已取消任务仍占用真实工作线程，直到实际调用返回，不会仅因Future被取消就虚假释放本地工作线程。客户端返回也不能证明远端已停止计算，因此取消后的立即重试仍可能遭遇供应商限流。供应商连接/读取超时应另行配置，线程空闲回收时间不能代替请求超时。

## 默认参数

```yaml
agent:
  embedding:
    execution:
      core-pool-size: 8
      max-pool-size: 8
      queue-capacity: 16
      keep-alive-seconds: 60
      per-article-parallelism: 4
      batch-size: 16
      article-timeout: 120s
  index-outbox:
    consumer-concurrency: 4
spring:
  rabbitmq:
    listener:
      simple:
        prefetch: 1
        acknowledge-mode: auto
```

本地`application.yml`与示例配置均通过 `EMBEDDING_CORE_THREADS`、`EMBEDDING_MAX_THREADS`、`EMBEDDING_QUEUE_CAPACITY`、`EMBEDDING_ARTICLE_PARALLELISM`、`EMBEDDING_ARTICLE_TIMEOUT`、`ARTICLE_INDEX_CONCURRENCY` 覆盖；代码默认值也同步修改。索引消费者默认固定4个，与联合对照中的固定消费者口径一致。修改这些配置需要重启Java。

| 参数 | 选择理由 |
|---|---|
| 核心/最大线程8/8 | 将本实例文章索引的并发预算设为8；容量100的模拟混合场景中8线程比旧方案更快，继续到16线程收益较小。固定池避免最大线程长期不启用 |
| 队列16 | 正常最多4个消费者×每篇4批，共16批在途；8个执行、其余排队，并留有提交/完成时间差的余量。额外调用者仍可能填满队列并触发拒绝 |
| 每篇4批 | 单篇能同时执行最多4批，多篇共享8个线程；保留窗口上限，限制长文占用的排队空间 |
| 每批16块 | 沿用已有批量请求规模，线程数不等于分块数 |
| 空闲回收60秒 | 仅影响超过核心线程数的空闲线程；默认核心=最大，所以不会回收这8个核心线程 |
| 拒绝AbortPolicy | 显式失败，交给既有重试。CallerRuns会把向量化放到消费者线程，突破专用池的并发边界；Discard会静默丢任务 |
| 向量阶段总超时120秒 | 限制消费者的等待时间，超过则失败；供应商超时/吞吐低时需按实际配额与文章长度调整 |

这里的8线程只限制本实例的**文章索引**入口。Java查询向量、Python查询向量、其他Java实例如果共用API Key，仍要一起计算供应商并发/RPM/TPM配额。不能因服务器有更多CPU就直接调大线程数。当前使用MySQL连接持有文章锁，增加MQ消费者也会增加被长期占用的数据库连接数。新默认值依据模拟测试选择，未完成真实模型及数据库/ES的联合压测。

模拟HTTP耗时固定在60～100ms，常规场景假设供应商允许4个并发请求，超限返回429。记录全部成功/失败、文章P50/P95、整批负载耗时、实际供应商调用数/429、线程池最大线程数、每2ms采样的活跃线程/排队峰值，并保存每篇任务耗时。首个HTTP请求用于预热，不计入对比。

失败请求很快返回可能让P95看起来更低，必须先比较成功率，再比较耗时。此测试能说明线程池参数的取舍，不能证明真实供应商的最优线程数或生产吞吐。实配前需要测实际Embedding延迟、429、RPM/TPM、排队时间及数据库连接余量。
