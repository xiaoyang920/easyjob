# Agent 重启后的 RPC 恢复

Python 的 `/health` 恢复不代表 Java 中缓存的 Dubbo Reference 已经恢复。快速重启时 Consul 中的地址可能始终保持相同，但旧连接已被 Dubbo 移入不可用列表。只按地址缓存 Reference 会让后续请求继续命中这个失效资源。

当前连接池在遇到同步 RPC 传输异常或流式 observer 错误时，将对应资源标记为失效。已有调用释放后销毁旧 Reference，下一个请求为相同地址创建新连接。健康目录不能把已经确认失效的资源重新激活；旧调用继续释放资源时也不会重复关闭它。

业务错误仍通过 Reply/Frame 的 error 字段传递，不因参数或权限错误回收正常连接。失败请求不会被自动重放，尤其不重试保存、审批等状态变更；只读验收探针可以主动检查连接恢复。

## 防止重启中断新请求

`scripts/restart-agent.ps1` 通过 `agent-restart-guard.py` 持有 `agent_execution_gate` 的同一行锁。取得锁后，同时检查运行记录与有效的接入租约：运行、准备或排队的请求存在时拒绝重启，不能只凭之前的一次空闲查询或执行租约到期判断。

该锁覆盖空闲检查、停止旧进程、启动新进程到健康检查完成；新的执行请求在这段时间等待接入，因此不能在检查后抢先进入旧进程。已有待审批的草稿保留检查点。脚本失败、正常结束或父进程关闭标准输入都会释放锁；保护进程也有超时。`KeepAlive` 等待服务存活发生在释放锁之后。

仅运行 `agent-idle-check.py` 不能消除检查与停止进程之间的并发窗口，实际重启必须使用带接入保护的脚本。

## 重启完成的就绪条件

`restart-agent.ps1` 在 Python `/health` 成功后，继续执行 `agent-rpc-ready.py`。该脚本通过服务密钥认证的 Java `/internal/agent/ready`，调用实际 `AgentRpcClient.overview`，连续两次成功才释放接入锁、报告重启成功。它会在 25 秒总期限内重试只读探针，使旧 RPC Reference 的失效和重建发生在预热阶段；不重放任何用户聊天、保存或审批。探针不调用 LLM，不创建账号，不返回 overview 中的数据。

必须先部署包含该内部端点的新 Java 构建；401/403/404 立即失败，超时也不能报告重启成功。进程已启动但 RPC 未就绪时脚本会报错。此机制覆盖通过受保护脚本进行的本地重启，不能保证任意突发断网、进程崩溃或其他方式重启时的请求都成功。

## 验证

- `RpcPeerPoolTests` 包含相同地址的失效连接替换、在途调用排空和迟到错误回调，合计 7 项测试。
- `tests/test_restart_guard.py` 覆盖新请求与重启竞争的两个顺序、准备／排队租约、缺失控制行、异常／取消释放和父进程结束。
- `scripts/rpc-restart-http-smoke.py --restart-agent` 使用临时账号实际重启空闲 Python Agent，检查网关到 Java 到 Agent 的只读调用恢复，再用真实 MySQL 中的失败运行记录验证“继续”的请求准备。测试不调用 LLM，结束后清理自己的账号和会话。
- 结果记录在 `logs/rpc-restart-http-smoke.json`。后台重启器的输出写到文件，避免 Windows 子进程继承输出管道导致验收脚本无法退出。
- 冒烟脚本现在要求重启完成后的第一个网关请求直接成功，不再通过重试隐藏首次 502；`--output` 可为每次实测保留独立报告。
