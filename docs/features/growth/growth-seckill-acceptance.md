# 秒杀模块第四轮验收

验收脚本为 `scripts/growth-seckill-lab.py`，测试宿主为 `src/test/java/com/easyjob/growth/GrowthLabApplication.java`。宿主复用生产订单、事务、MyBatis Mapper、Lua、RabbitMQ 消费与网关身份过滤器；只替换无关业务依赖的管理员门面，并在测试类中增加事务提交后阻塞点和实例标签。测试钩子不进入生产 JAR。

## 隔离和边界

- 每次运行创建专属 MySQL 库及账户、带归属标签的 Redis 和 RabbitMQ 容器，使用随机本地端口。清理前核对名称、标签和归属文件，只删除本次资源。
- 真实 Gateway 验证临时 RSA JWT，真实 Auth 在线查询测试会话及 MySQL 账号。测试会话在准备阶段写入独立 Redis，不把密码登录和验证码作为订单压测内容。
- 两个独立 JVM 运行相同订单代码，网关轮询分配。两个实例、网关及 Auth 各设 256 MB 最大堆、2 个 JVM 可见处理器。MySQL 共用本地主机，数据和运行账户隔离，因此结果不是独立物理服务器的生产容量。
- 容量测试临时网关将单用户阈值调为 20000 次/分钟、对应单 IP 60000 次/分钟，避免所有合成用户共用一个本机 IP 时先触发限流。正式配置没有改变。故障 TCP 代理独立运行，避免与压测客户端共用事件循环；延迟包含网络、客户端连接池和代理开销。
- Redis 使用 AOF，`appendfsync=always`，无淘汰。RabbitMQ 使用现有经典持久队列。覆盖单节点重启恢复；不等于已完成 Sentinel、Redis Cluster、RabbitMQ 多副本故障切换认证。

## 验证矩阵

| 场景 | 验收依据 |
|---|---|
| 1000 请求 / 32 并发、5000 / 128、10000 / 256 | 每场 200 库存，唯一订单和用户数均为 200，两实例均有流量，无系统错误 |
| 消费者提交后、ACK 前崩溃 | 在真实提交返回后阻塞，确认数据库已存在订单，强制终止该 JVM；另一实例收到 RabbitMQ 重投，库存不重复扣减 |
| Redis 实际进程崩溃重启 | 待发送预占尚未落库时 SIGKILL Redis 容器，使用同一 AOF 重启；凭据、Stream 和库存保留，后续只落单一次 |
| RabbitMQ 实际停止/启动 | 停止独立 Broker 后受理请求，Stream 保留待发送意图；Broker 重启后落库并对账收敛 |
| 发布确认网络丢失 | TCP 代理丢弃 Broker 到应用的流量，模拟消息可能已接收但确认不可达；待发送记录保留，恢复网络后无重复扣库存 |
| Redis 网络隔离 | 应用到 Redis 的连接被切断时拒绝准入，恢复后可以继续，未凭空补库存 |
| 暂停期间的未确认预占 | Broker 断开时先受理，再暂停；恢复后拒绝落单并补偿，暂停状态也能对账收敛并恢复 |
| 支付锁等待跨截止时间 | 独立 SQL 连接锁住订单并修改截止时间，支付进入锁等待，跨过截止后释放；不得扣款 |
| 支付与关单并发 | 60 张订单在截止时间前、附近、之后并发重复支付，真实关单任务同时运行；最终同时出现 PAID/CLOSED，账、成长、库存与终态一致 |

压力结果区分 HTTP 请求吞吐量与最终落单吞吐量；200 响应包含重复受理，不能当成成交量。延迟统计包含业务拒绝，故同时保留响应码分布。记录 P50/P95/P99、观察到的队列 ready/unacked、Stream 积压及各 JVM 的 CPU 时间和内存。采样峰值可能低于真实瞬时峰值。

## 重跑

先构建真实 Auth、Gateway 与根 Java 的测试类。根工程使用现有隔离构建目录：

```powershell
mvn -Deasyjob.build.directory=target/growth-build -DskipTests test-compile
mvn -Deasyjob.build.directory=target/growth-build -DincludeScope=test -Dmdep.outputFile=target/growth-lab-classpath.txt dependency:build-classpath
.\python-agent\.venv\Scripts\python.exe scripts\growth-seckill-lab.py
```

需要本地 Docker 管理权限和维护数据库权限，测试容器复用已缓存的 `redis:7.4`、`rabbitmq:4.1-management` 镜像。脚本默认执行完整矩阵，结束后清理资源。每次运行的证据保存在忽略目录 `temp/easyjob-growth-lab-<编号>/report.json`，失败结果也会保留，不把失败运行计入通过数量。

## 本轮修复

原补偿 Lua 只接受正常活动标记，暂停后会阻塞库存释放；现允许暂停状态下继续幂等补偿，库存或凭据缺失时仍拒绝处理。原支付锁定 SQL 中的 NOW 在等待锁之前求值；现拿到订单锁后用新语句按数据库时间重新检查截止时间，防止排队中的支付跨期后仍扣款。

多实例压力还发现：重复消费者在 `INSERT IGNORE` 等待另一事务提交后，普通查询可能仍读取先前的可重复读快照，误判订单不存在并释放有效预占。现改为当前锁定读。修复前出现了数据库库存为 0、Redis 库存却被补回的情况；数据库条件更新阻止了实际超卖，但不能靠它掩盖错误放行。修复后的三档压力均只产生 200 张唯一订单，Redis 与数据库库存一致。

## 最终实测（2026-10-28）

完整矩阵通过 28 项检查，另有 32 项 Java 回归通过。可复核数据见 [验收数据](../../validation/growth-seckill-20261028.json)。失败的开发运行没有计入通过数量。

| 请求数 | 并发数 | HTTP 请求/秒 | P95 | P99 | 最终唯一订单 | 系统错误 |
|---:|---:|---:|---:|---:|---:|---:|
| 1000 | 32 | 246.12 | 188 ms | 219 ms | 200 | 0 |
| 5000 | 128 | 220.84 | 1750 ms | 3235 ms | 200 | 0 |
| 10000 | 256 | 204.54 | 4016 ms | 6422 ms | 200 | 0 |

每个档位均有两个实例处理请求，响应码只有 200 和售罄 409；200 包含重复受理。观察到的 Stream 积压峰值分别为 122、109、104。MQ ready/unacked 的采样峰值均为 0，不代表从未有过短暂排队。JVM 的 CPU 时间、按单核计算的 CPU 比例、RSS 和私有内存均保存在数据文件；虚拟环境代理启动器的计数不作为资源结论，后续运行已改为直接启动实际解释器。

消费者提交后被强制结束，另一实例实际收到重投，数据库仍只有一单；Redis SIGKILL 后用 AOF 恢复了未落库的凭据及 Stream；Broker 停止期间的意图在重启后完成；单向丢弃发布确认及 Redis 断网后也恢复收敛。暂停期间补偿通过。60 张竞争订单最终为 20 张 PAID、40 张 CLOSED，扣币、成长和归还库存均与终态一致；另一个支付锁等待跨截止的订单关闭且未扣币。

并发升高后吞吐没有同比提高，P99 明显上升；本轮证明了给定压力下的一致性和恢复行为，没有证明容量线性扩展或满足生产延迟 SLO。上述数值来自同一台开发机上的客户端、代理、四个 JVM 和共享 MySQL，不应换算为生产 TPS。隔离容器、数据库、账户和进程已清理。

后续补了关联 trace 的分段诊断，主要发现发送请求头之前的压测端等待；此前端到端尾延迟不能据此归因于业务 Java 容量不足。计时范围、原始数据和限制见 [Caffeine 与 P95 核对](growth-caffeine-latency.md)。

三处修复已通过已验证构建顺序重启本地 Blog。发布后现有 27 项真实接口检查再次全部通过；前端、Gateway、Auth、Blog、Agent 均返回健康状态 200。核对临时 MySQL 库及账户残留数量均为 0，生产 JAR 不包含 `GrowthLabApplication` 测试故障钩子。旧的 3101 测试 Vite 也已关闭。
