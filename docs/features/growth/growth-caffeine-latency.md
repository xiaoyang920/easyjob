## 为什么不能把之前 P95 上升直接归因于 Java 扛不住

此前测量的是端到端 HTTP 延迟，没有分开客户端发送前等待、网关认证与转发、业务处理。本次在独立环境关联同一请求的 trace：

- 客户端计时：获得压测并发槽后，至读完响应；不包含压测队列里等待取得并发槽的时间。
- 发送前计时：从构造 HTTPX 请求到 HTTP/1.1 请求头开始发送，包含客户端池/连接取得、建连及调度等。不能仅凭这个总数再断定是哪一种客户端机制。
- 网关计时：GlobalFilter 进入至响应完成，包含认证和上游转发；不包含请求进入过滤器之前的入口等待。
- 业务计时：可信身份过滤之后至 MVC 响应生成，包含业务中的 Redis/MySQL 等待；不包含 Tomcat 开始执行过滤器前的排队和网络写出。

仅测试宿主增加响应缓冲计时头，测试网关开启 trace 耗时日志，生产包不包含诊断过滤器。诊断增加了额外采集开销，不构成与旧版本同条件的 Caffeine 性能对照。

## 实测结果

第一组 10000 请求、256 并发，10000 个 trace 全部匹配：端到端 P95 4531 ms、网关计时 P95 51 ms、业务处理 P95 11.71 ms。

随后增加发送事件计时，再跑 3000 请求、256 并发，3000 个 trace 全部匹配：

| 计时范围 | P95 | P99 |
|---|---:|---:|
| 端到端 | 6406 ms | 9313 ms |
| 请求头开始发送之前 | 6234 ms | 9063 ms |
| 请求头开始发送之后至响应读完 | 500 ms | 891 ms |
| 网关过滤器内，含认证与上游 | 250 ms | 628 ms |
| 订单业务处理 | 22.75 ms | 32.69 ms |

这些是各自的分位数，不能直接相加或相减。以同一条最慢请求为例：客户端总耗时 18641 ms，其中请求头发送前 18531 ms，网关记录 23 ms，业务处理 2.6573 ms。因此这条请求的大部分等待发生在发出请求头之前，而不是订单方法内部执行了十几秒。

本次主要观察到压测端发送前等待。它不支持“业务 Java 的执行耗时已经达到几秒”或“Redis Lua 执行了几秒”的结论，也不证明所有其他环境中的服务线程池、连接池都不会饱和。若要判断生产容量，需要使用独立压测机，并继续细分连接取得/建连、网关入口队列、Tomcat 忙线程、上游池和依赖等待。

两次诊断均由两个业务实例处理，只有正常受理和售罄响应，每场最终 200 张唯一订单，Redis 与数据库库存一致。诊断不重跑已经完成的全部故障矩阵。结构化结果见 [分段计时数据](../../validation/growth-caffeine-latency-20261028.json)。
