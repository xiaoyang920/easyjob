# 阅读等级与文章访问控制

当前实现按累计有效阅读时间升级，不做等级衰减。数据库迁移为 `python-agent/migrations/010_reading_levels.sql`，通过 `python -m app.migrate` 执行；迁移已经在本地执行。

## 使用方法

- 登录后阅读他人的已发布文章，文章详情页右侧显示自己的阅读等级、累计时间及升级进度。
- 个人空间右侧展示该用户的阅读成长进度。
- 管理员打开文章详情，在正文下面的“最低阅读等级”选择等级并保存。普通作者不能修改这个设置。
- 等级不足的用户仍可看到标题、作者、封面及公开摘要，正文位置显示解锁提示。
- 现有文章默认 L0；以前的观看量没有可靠的阅读时长，因此不换算为成长时间。

默认规则如下，均为从注册以来累计的总时长，而不是每一级额外所需时长：

| 等级 | 累计有效阅读 |
| --- | --- |
| L0 | 0 |
| L1 | 1 小时 |
| L2 | 5 小时 |
| L3 | 20 小时 |
| L4 | 50 小时 |

规则存放在 `reading_level_rule`。目前提供文章门槛设置界面，未提供等级规则编辑界面。等级算法为 `max(已获得等级, 当前总时长满足的最高等级)`，即使以后调高时间门槛，也不会降低用户已获得的等级。

## 为什么分开保存时间和等级

`total_millis` 是累计事实，`earned_level` 是已经获得的资格。每次增加有效阅读时间，在同一事务中重新计算并保存等级。毫秒累计避免频繁短间隔心跳被逐次取整丢失；接口展示时再换算为秒。

新增的数据结构：

| 表或字段 | 职责 |
| --- | --- |
| `article_info.required_level` | 每篇文章要求的最低等级，默认 0 |
| `reading_level_rule` | 等级与累计秒数门槛 |
| `user_reading_progress` | 每个用户一条：累计毫秒、已获得等级、当前有效阅读会话 ID |
| `reading_session` | 每次开始计时的一条记录：文章、用户、最后心跳时间、序号、活跃状态及本次累计量 |
| `user_reading_daily` | 每用户每天的累计毫秒，用于核对统计，按上海日期归档 |

这里的 reading_session 是阅读计时会话，与 AI 的 conversation、run 无关。

## 一次阅读怎样变成累计时间

1. 前端拿到允许阅读的文章详情后，向 `POST /api/reading/sessions` 发送 articleId 和 active。用户身份由 JWT 提供，前端不能指定 userId。
2. 后端验证文章已发布、未删除、用户等级足够，且不是用户自己的文章，再生成阅读会话 UUID，并记下服务器时间。
3. 前端每 5 秒检查页面状态，通常每 15 秒向 `POST /api/reading/heartbeat` 发送 sessionId、sequence 和 active。状态改变时立即尝试发送。
4. 后端根据“本次服务器时间 − 上次服务器时间”计算间隔，前端没有上传时长的参数。
5. 如果上一次状态为活跃、间隔大于 0 且不超过 45 秒，就计入 `min(间隔, 30 秒)`；否则计入 0。更新最后时间、当前活跃状态和序号。
6. 在同一个事务中增加用户累计时长、升级资格、当天时长及本次阅读会话时长，然后将新进度返回前端。

例如 10:00:00 开始，10:00:15 收到心跳，可累计约 15 秒。10:00:20 切换后台并成功发送 active=false，可再累计切换前约 5 秒；下一次心跳不会累计后台间隔。恢复前台的心跳将 active 改回 true，此后重新计时。

如果关掉页面，5 分钟后才重新发送心跳，超过 45 秒的间隔计入 0，不会补足这 5 分钟。40 秒的延迟最多计入 30 秒。

前端的活跃条件是：页面可见、窗口有焦点，并且最近 120 秒内发生过鼠标、键盘、滚动或触摸操作；每 5 秒检查一次，因此空闲暂停检测存在最多约 5 秒延迟。后台切换尽量即时上报，断网或关闭浏览器时的最后一段只能尽力上报。

## 并发与重复请求怎样处理

所有计时更新先锁住 `user_reading_progress` 的用户主键行：用 INSERT ... ON DUPLICATE KEY UPDATE 直接取得写锁，再 SELECT ... FOR UPDATE 读取状态。这避免 INSERT IGNORE 先取共享锁、随后多个请求同时升级写锁造成死锁。

同一用户只有一个 active_session。打开第二个阅读页并开始计时，会替换第一个阅读页的会话 ID；旧页之后的心跳返回 409 并停止计时。这是“最新开始计时的页面持有计时资格”，不是两个页面同时累计。旧页恢复计时需重新打开或刷新。

每个会话保存 last_sequence。相同或更小序号只返回现有进度，不增加时间。前端发生超时后保留原来的请求体和序号重试，避免服务器已经提交、客户端却不知道时重复累计。前端也限制同一个页面最多一个心跳请求正在发送。

序号用于去重，不用于计算时长。把序号改成一个非常大的数字不会让用户获得更多时间。

## 文章权限在哪里控制

`ArticleAccessService` 在后端判断：公开文章、达到等级、文章作者本人、有效管理员，满足任意一个条件即可阅读；作者和管理员可以管理正文，但这不等于可以通过无资格文章赚取成长时间。

文章详情缓存保存共享的原始数据。每个请求复制一份详情对象，然后从 MySQL 读取最新门槛，按当前用户身份校验；没有权限就将 content 设为 null。因此前端即使绕过隐藏逻辑，也拿不到正文，管理员调整门槛后不会因旧缓存继续放行。

管理员角色使用项目现有约定 `role=2`，并核验账号 status=1。后端设置接口为 `PUT /api/article/{articleId}/reading-level`，只接受规则表中已有的等级。普通文章创建、编辑 DTO 不包含 requiredLevel，避免作者通过额外 JSON 字段修改管理员策略。

首页、推荐、搜索和空间列表可以展示等级文章的公开信息；观看量接口及计时开始、心跳接口也会校验文章权限。阅读观看量与阅读成长分开计算，原有观看量去重规则保持独立。

## AI 的边界

本次没有实现 AI 的用户阅读等级授权。为避免绕过正文权限，required_level > 0 的文章暂不提供文章 AI 问答，也不进入 AI 文本块索引。

Python 在文章来源加载、召回候选回查和最终引用版本校验三个位置排除等级文章。即使异步删除索引还没完成，旧候选也不会直接进入 Reranker 或模型。普通站内搜索仍可展示其标题及公开摘要。

## 验证与复现

新增计时边界、等级不降级、权限脱敏等测试。当前 Java 96 项、前端 51 项、Python 374 项测试通过，前端类型检查及生产构建通过。Java 测试未运行需要完整应用环境的 EasyjobApplicationTests。

真实接口脚本为 `scripts/reading-level-check.py`，执行：

```
python-agent\.venv\Scripts\python.exe scripts/reading-level-check.py
```

脚本创建独立账号和文章，运行 30 项真实 HTTP/MySQL 检查，结束后删除样例数据和相应 ES 索引文档。通过修改样例会话的最后心跳时间模拟间隔，不等待几十小时，也不改真实用户时间。覆盖 10 个并发相同心跳只累计一次、暂停/断线、跨用户和跨标签页、升级解锁、缓存门槛变化及 AI 候选权限过滤。实测报告为 `logs/evaluation/reading-level-20261005-115719.json`。

界面已检查等级不足提示和个人空间进度面板。

## 当前限制

可见性和操作活跃状态仍是浏览器上报的信息，无法证明用户真的读懂文章，也不能完全阻止脚本伪造行为。服务器计时、单会话和序号去重防止基础的重复累计及虚报时长；如将来把等级用于付费权益，需要另行强化防刷策略。

阅读会话记录目前保留为核对数据，尚未增加定期归档任务。每日汇总按间隔结束时的上海日期归属，跨午夜最多一个心跳间隔计入次日，总累计时间不受影响。
