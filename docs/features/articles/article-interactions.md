# 点赞、收藏与索引热度

## 请求流程

前端提交明确目标：`POST /api/action/article/{id}/like?active=true` 或
`POST /api/action/article/{id}/collect?active=false`。成功返回
`data: { "active": true, "count": 6 }`，页面使用服务端状态与计数更新按钮，等待期间禁用重复点击。
未传 `active` 的旧调用保留切换语义；只有明确提交目标状态才具备重复请求幂等性。

后端事务先通过 Mapper XML 对文章行执行 `SELECT ... FOR UPDATE`，确认文章公开且未删除，
再读取当前用户的关系（`article_id + comment_id=0 + action_type + user_id`）。
目标与现状一致时直接返回，不重复计数、通知或投递任务。
确需变更时，同一个 MySQL 事务完成关系增删、文章计数更新、`article_index_outbox` 的
`COUNTS` 任务写入和通知入库。任一步失败则事务回滚；取消操作不发新增通知。

## 缓存与异步投影

点赞、收藏不删除文章正文缓存。详情接口原有的动态查询仍从 MySQL 读取最新计数和当前用户状态，
这些字段不依赖正文缓存过期。此改动没有将 MySQL 计数迁移到 Redis。

HTTP 请求不调用 ES 和向量索引。现有 Outbox Relay 每批最多领取 10 个任务，经 RabbitMQ
`article.update` 路由发送；消费者与文章完整索引、删除共用文章级索引锁。
消费者重新读取 MySQL 的最新点赞、收藏绝对值，覆盖文章 ES 文档和已有文本块的计数，
不重新分块、不调用 Embedding，也不创建残缺 ES 文档。

重复或乱序消息不会按增量再加一次；取消后的更小计数也会正常覆盖。
ES 写入异常、文本块更新超时、部分失败或版本冲突都会使任务保持未完成，由现有重试链路处理。
只有两处索引均同步成功才完成任务。文章已下架、删除或不存在时，延迟热度任务直接完成，
不会恢复文章的可见性；文档创建和清理由文章生命周期任务负责。

这里保证的是索引最终一致。详情页使用数据库的新计数，搜索排序可能短暂使用旧热度。
沿用既有最多 8 次投递与退避策略；耗尽后任务进入 `dead`，可在管理端排查、重试。
大量互动场景下仍需监控积压，后续可按文章合并热度任务或拆出独立队列。

## 验证与启用

使用项目 Python 环境运行：

```powershell
python-agent/.venv/Scripts/python.exe scripts/test-article-interactions.py --mysql
```

脚本读取本地环境中的 MySQL 连接信息，密钥只通过进程环境传递。
真实数据库测试仅允许本机 MySQL，创建随机 `easyjob_interaction_test_*` 数据库，结束后删除该临时库；
不写应用业务库。覆盖 24 个相同用户的并发重试、24 个不同用户的添加与取消、
事务内写入任务后故障的完整回滚。其余回归覆盖公开性、关系隔离、任务完成时机、
索引部分失败、绝对值覆盖和既有文章详情行为。
不带 `--mysql` 可只运行离线回归。CI 也执行真实 MySQL 测试。

复用既有任务表和 MQ 绑定，无需新增表或修改现有表结构。
后端需运行新构建的 JAR；前端需使用本次源码或新构建产物。
